# Api monitor для [DSH]

[English](README.md) · **Русский**

Плагин для [DSH], который показывает все исходящие запросы к API-эндпоинтам прямо во вкладке правой панели: адрес, метод, **все** заголовки, исходное JSON-тело и ответ.

Страницы моделей и сессий говорят, что запрос *был*. Этот плагин показывает, что именно *ушло по проводу*, — включая заголовок `Authorization` и полное тело промпта, которых в провайдерских просмотрах нет.

> Нужен настольный DSH с веб-интерфейсом (приложение Desktop или `dsh web`). Обычный ESM, без сборки и зависимостей.

## Где это появляется

- **Правая панель → страница Start**: карточка **Api monitor**, сразу после *Browser*. Нажатие открывает монитор вкладкой в этой же панели.
- **Левая панель, внизу**: кнопка с пульсом рядом с настройками. Открывает ту же вкладку из любого места.

Вкладка — это список запросов и карточка выбранного запроса:

| Вкладка | Что показывает |
| --- | --- |
| **JSON запроса** | Весь обмен одним документом: адрес, метод, заголовки, тело, ответ, ошибка |
| **Заголовки** | Заголовки запроса и ответа таблицами |
| **cURL** | Готовая команда, воспроизводящая запрос из терминала |
| **Ответ** | **Собранный ответ**, а сырой поток — в один клик |

Над карточкой: живой фильтр, пауза, экспорт в `.json` и очистка.

### Как читать потоковый ответ

Провайдер со стримингом отвечает сотнями мелких SSE-кадров, и в сыром виде это нечитаемо. Host складывает эти кадры обратно в ответ, который реально выдала модель, поэтому вкладка **Ответ** открывается на читаемом тексте:

- дельты склеиваются по порядку, включая типизированные события Anthropic и форму `candidates` у Gemini;
- текст *рассуждения* хранится отдельно и свёрнут под **Рассуждение**;
- вызовы инструментов собираются из фрагментов и перечислены в **tool calls**;
- в строке состояния видны статус, длительность, модель, причина `finish`, расход токенов и сколько кадров склеено;
- кнопка **Сырой поток** переключает на исходные кадры, **Собранный** — обратно.

### Поиск

Во всех вкладках один и тот же поиск: набор подсвечивает все совпадения жёлтым, `Enter` / `Shift+Enter` (или кнопки ‹ ›) переходят по ним, `Esc` очищает. Счётчик показывает `3/17` и прокручивает текущее совпадение в вид. Поиск идёт по тому, что показывает вкладка: JSON запроса, обе таблицы заголовков, команда cURL, собранный ответ и его рассуждение (а при активном режиме — и сырой поток).


## Установка

Плагин — это каталог-бандл: обычный ESM, без сборки и зависимостей.

```sh
git clone https://github.com/avego/dsh-api-monitor.git
```

Дальше либо:

- **через интерфейс**: Настройки (шестерёнка внизу левой панели) → **Плагины** → **Добавить плагин** → выбрать склонированный каталог;
- **либо поручить агенту**: `plugin_manager` с `action: install_bundle` и `target`, равным абсолютному пути.

Требования: развёртывание с веб-интерфейсом (приложение Desktop или `dsh web`) — host-части нужен сервис `webServer`. В headless- и SDK-профилях нет ни веб-сервера, ни правой панели, поэтому работать там нечему.

Изменения применяются ко всему профилю и сохраняются после перезапуска. Имя пакета — `@local/dsh-api-monitor`: он ставится из каталога, а не из реестра, поэтому шага публикации здесь нет и второго канала установки, который пришлось бы синхронизировать, тоже.

## Что перехватывается

Host-часть подменяет две точки входа процесса:

1. `globalThis.fetch` — через него работают все HTTP-SDK (OpenAI-, Anthropic- и Gemini-совместимые клиенты, провайдеры на `fetch`);
2. `node:http` / `node:https` `request` — код, который собирает запросы вручную.

Каждый вызов становится одной записью. Запись создаётся при отправке и обновляется, когда приходят заголовки ответа и когда прочитано превью, поэтому запрос «в процессе» виден сразу, со статусом `pending`.

Запись выглядит так (сокращено, токен скрыт):

```json
{
  "id": "req_mwrn3x1k_2",
  "timestamp": "2026-11-22T08:25:41.045Z",
  "host": "plusvibeapi.ru",
  "url": "https://plusvibeapi.ru/v1/chat/completions",
  "method": "POST",
  "headers": {
    "accept": "application/json",
    "authorization": "Bearer sk-…",
    "content-type": "application/json",
    "user-agent": "deepseek-harness/0.2.2-rc.3",
    "x-stainless-arch": "x64",
    "x-stainless-lang": "js",
    "x-stainless-runtime": "node"
  },
  "body": {
    "model": "deepseek-v4.1-flash",
    "messages": [
      { "role": "system", "content": "You are an AI agent powered by [DSH]…" },
      { "role": "user", "content": "проведи анализ проекта" }
    ]
  },
  "durationMs": 4688,
  "pending": false,
  "responseStatus": 200,
  "responseStatusText": "OK",
  "responseHeaders": { "content-type": "text/event-stream; charset=utf-8" },
  "responsePreview": { "…": "первые 64 КиБ ответа" },
  "responseBytes": ">=65700",
  "error": null
}
```

### Поля записи

| Поле | Значение |
| --- | --- |
| `id` | `req_<время в base36>_<номер>` |
| `timestamp` | ISO 8601, момент вызова |
| `host` | Имя хоста из URL, для группировки |
| `url` | Полный URL вместе с query-строкой |
| `method` | HTTP-метод в верхнем регистре |
| `headers` | Заголовки запроса: имена в нижнем регистре, по одной строке на значение |
| `body` | Разобранный JSON, если тело — JSON; иначе исходный текст; `null`, если тела нет |
| `durationMs` | Время до прихода заголовков ответа |
| `pending` | `true`, пока запрос ещё выполняется |
| `responseStatus` … `responseStatusText` | Статус ответа |
| `responseHeaders` | Заголовки ответа в том же виде, что `headers` |
| `responsePreview` | Начало сырого ответа, до 256 КиБ; разбирается как JSON, если это JSON |
| `responsePreviewTruncated` | `true`, если сырое превью обрезано на этом пределе |
| `responseBytes` | Сколько байт ответа прочитано |
| `responseIncomplete` | `true`, если чтение остановилось на пределе перехвата и ответ может быть неполным |
| `responseAssembled` | Потоковый ответ, склеенный в текст: `kind`, `text`, `reasoning`, `model`, `finishReason`, `usage`, `toolCalls`, `frames`, `done`, `incomplete` |
| `error` | Ошибка транспорта или закрытие соединения до ответа |

Тела разбираются, а не хранятся строками, поэтому и в интерфейсе, и в экспорте сохраняется исходная структура JSON. Тело больше 8 МиБ хранится как `{ "truncated": true, "characters": N, "preview": "…" }`.

## HTTP-маршруты

Клиентская часть читает буфер по трём маршрутам того же веб-сервера, что отдаёт интерфейс, поэтому к ним можно обращаться и скриптами:

| Маршрут | Метод | Ответ |
| --- | --- | --- |
| `/api/api-monitor/requests` | `GET` | `{ ok, count, requests: [...] }`, новые первыми |
| `/api/api-monitor/requests` | `POST`, `DELETE` | Очищает буфер, `{ ok: true }` |
| `/api/api-monitor/clear` | `POST` | Очищает буфер, `{ ok: true }` |
| `/api/api-monitor/events` | `GET` | `text/event-stream`: `init`, `new-request`, `update-request`, `cleared` |

```sh
curl -s http://127.0.0.1:<порт>/api/api-monitor/requests | jq '.requests[0].headers'
```

Маршруты живут вне Remote-шлюза и собственного токена сессии не имеют. Поэтому они отвечают **только loopback-запросам** (`127.0.0.0/8`, `::1`, `::ffff:127.*`), а на всё остальное возвращают `403`. При этом прочитать их может любой локальный процесс — см. [Безопасность](#безопасность).

## Настройка

Значения по умолчанию лежат в `cordis.patch.yml` бандла:

```yaml
- insert:
    - id: api-monitor
      name: '@local/dsh-api-monitor'
      config:
        maxEntries: 200          # по умолчанию 100, максимум 2000
        maxTotalChars: 67108864  # по умолчанию 48 МиБ, максимум 512 МиБ
```

- `maxEntries` — сколько запросов остаётся в буфере.
- `maxTotalChars` — общий бюджет на сохранённые тела и превью. При его превышении удаляются самые старые записи, поэтому несколько огромных промптов не раздуют процесс.

Править файл внутри бандла можно для пробы, но `git pull` его перезапишет. Чтобы значение сохранилось, перекройте ту же строку `api-monitor` в патче **своего профиля** — этот слой ваш и переживает обновления.

## Как это устроено

**Host-часть** (`index.js`) оборачивает `globalThis.fetch` и точки входа `node:http`/`node:https` `request`, приводит каждый вызов к записи и держит ограниченный буфер в памяти. Обёртки прозрачны: запрос уходит без изменений, вызывающий получает исходный объект ответа, а тело ответа читается только через `Response.clone()`, с ограничением и последующей отменой. Сбой перехвата никогда не ломает сам вызов. Склейка ответа тоже происходит здесь, при чтении, поэтому клиент получает готовый текст, а не кадры.

**Клиентская часть** (`client.js`) — браузерный модуль: регистрирует тип вкладки правой панели (`api-monitor`) с карточкой на странице Start, тело вкладки, её заголовок и одну кнопку в футере левой панели. Данные берёт по маршрутам выше и следит за новыми вызовами по SSE, с опросом раз в 2,5 с как запасным путём. Рисует токенами темы хоста, тексты держит в своём пространстве локализации (английский и русский), при выгрузке снимает все регистрации.

## Ограничения

- **Только процесс Host.** Перехватывается сам DSH, а не машина: трафик bash, терминалов и прочих подпроцессов не виден. Для этого нужен настоящий прокси.
- **Только вызовы `fetch` «на момент вызова».** Библиотека, сохранившая ссылку до загрузки плагина (`const f = globalThis.fetch` на импорте), обходит ловушку.
- **Не все клиенты.** Код, который не идёт ни через один из хуков — `undici.request()`, нативные HTTP/2-сессии, сокеты, внутренние пути `node-fetch` — не виден.
- **Тела-потоки не читаются**: вычитывание `ReadableStream` израсходовало бы тело у вызывающего.
- **Склейка покрывает частые форматы.** Кадры chat-completion ([OI]), `candidates` у Gemini, типизированные события Anthropic и события Responses склеиваются; необычный поток провайдера покажет сырые кадры, и текст может остаться пустым.
- **Сырое превью — 256 КиБ**, а на склейку читается до 4 МиБ потока. Дальше запись помечается `responseIncomplete`, ответ обрывается там, где оборвался перехват, и интерфейс это пишет.
- **Только память.** На диск ничего не пишется, после перезапуска список пуст.
- **Карточка `Api monitor` стоит после `Browser`**, а не под *More tools*: блок *More* панель всегда рисует последним, порядком карточек это не переопределить.

## Безопасность

В записях лежат секреты. Заголовок `authorization` содержит ваш API-ключ открытым текстом, а тело — весь промпт: код, учётные данные, всё, что вы вводили.

- Никуда ничего не отправляется: у плагина нет телеметрии и собственных исходящих вызовов.
- Маршруты отвечают только loopback и больше ничем не защищены — значит, **любой локальный процесс** может прочитать буфер, пока DSH запущен.
- **Экспорт пишет секреты на диск.** Держите выгруженные файлы вне репозиториев, трекеров и скриншотов.
- Нажимайте **Очистить**, когда закончили, и относитесь к буферу как к хранилищу секретов, а не как к логу.

## Разработка

Ни сборки, ни бандлера, ни зависимостей — правите файлы и перезагружаете.

```sh
node --check index.js
node --check client.js
```

Чтобы применить изменение, переключите строку плагина в **Плагинах** (выключить и снова включить) — так загружается свежая генерация модуля, — либо перезапустите DSH. Изменение клиентской части требует ещё и перезагрузки страницы.
